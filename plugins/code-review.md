# 通用代码审查

通用只读审查由宿主可用的独立角色执行。已登记 `code-reviewer` 的宿主调用该角色，其余宿主将本流程交给实际可用的独立子任务。它独立核对需求、差异和证据，并返回审查结论。每个项目提供适用的审查触发、编码规则、深审范围及验收门禁。角色指令限定只读操作，工具和权限由当前宿主及会话决定。

## 主 Agent 装配

1. 明确目标、验收范围、需求来源和已有验证。读取当前项目规则及 `code-review` 适配器。命中且启用前端规范时，按任务范围加载[前端共用规范](frontend-standards.md)和适用项目覆盖。
2. 在运行时和项目规则允许时，调用该宿主已启用的独立审查能力，提供任务范围、约束、适用入口和验证摘要。审查者独立核对证据，避免含有凭据的日志。适用规则要求独立审查而角色不可用时，将验收标为阻塞，主 Agent 可以继续独立的只读检查。
3. 将待修项交原实施者修正，并交原 reviewer 复审。汇总本任务结论、整体工作区状态、相关验证及未覆盖范围。

## 审查顺序

1. 确认目标、验收条件与审查基线，读取适用的仓库及目录指令。发现会影响验收的歧义时记录待确认项。
2. 每轮分别盘点已暂存、未暂存和未跟踪文件。工作区模式使用 `git status --short`、`git diff --cached --name-status`、`git diff --name-status`、`git ls-files --others --exclude-standard`。按项目规定和请求范围选择深审对象，读取其各层差异与新文件。重叠归属、公共依赖或影响不明时扩展查证。工作区盘点和全量深审是各自独立的结论。
3. 沿真实入口核对调用方、消费者、接口与数据兼容、状态所有权、异步顺序、异常、取消、重试、资源释放及适用权限。检查最小可复现条件与相邻分支，按影响面使用项目约定。足以判因的上下文需要完整阅读。
4. 承担本次交付验收时，按[需求审查与逐项验收](../acceptance.md)对照原始材料、人工决定、用户路径、最终差异与用例。从独立于实测结果的需求和项目用例检查计划是否完整；核对共用校验器对当前版本的报告，并查看原始证据是否支持各项预期。若有交互文档或设计稿，逐处检查 UI 到用例和实测证据的对应关系。核对修复前后的原失败项及受影响回归。发现遗漏、未执行或证据不足时，列明对应位置与用例，按本流程判定结论。仅受托静态审查时，报告约定范围的发现和未实测项，整体交付状态留给实际验收。核对验证命令、结果、运行范围及对应代码快照。先确认检查的实际行为，再在许可范围内做只读验证。代码变化、证据失效或覆盖不足时补验。记录无法执行的验证；测试通过只覆盖它实际验证的范围。
5. 审查者保持只读，禁止改文件、暂存区、依赖或外部状态。敏感材料仅记录位置与风险，不复述凭据。复审重新盘点并验证修复与可能回归，复用仍有效的证据。

## 结论与证据

- 先给结论和深审范围。发现按 P0（紧急）、P1（交付前修复）、P2（明确缺陷）、P3（非阻断建议）报告，并提供文件和行号、触发条件、实际影响、修复方向与验证方式。同一根因合并处理。
- 独立列出已满足、未满足、待确认、回归风险和未覆盖证据。整体状态仅在完整审查后判定，区分深审和仅盘点内容。
- `With fixes` 表示存在待修的已证实缺陷。`Blocked` 表示必要范围或关键证据缺失。`Ready` 表示约定范围满足需求且无待修缺陷。无法证实的判断如实记录。
