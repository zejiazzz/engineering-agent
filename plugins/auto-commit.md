# Git 交付 · auto-commit

## 授权范围

- 沿用当前任务的模型与推理设置。
- “生成 commit / 提交方案”只输出方案，不暂存、提交或推送。
- “提交代码 / commit / 帮我提交”授权明确任务范围的本地提交，不包含推送；“提交并推送”才包含两者。只要求推送时不自动创建提交。
- 复用已明确的文件范围与行为授权，不重复确认；存在无关改动、暂存冲突或推送目标不明确时，先完成可确定的只读准备，再说明缺失信息。
- 维护本 Skill 或讨论提交规范不构成执行 Git 写入的授权。

## 读取目标仓库约定

确认 Git 根目录和当前分支，读取适用的 `AGENTS.md` 及其导航的提交规范。按实际配置核对提交模板、校验器、hooks、CI、包管理器和验证命令；不要假设某个文件、工具或命令必然存在。

- 提交语言、格式、scope、标题长度、大小写与拆分阈值优先遵循仓库明确规定；未规定时参考近期提交和本次用户要求。
- 无明确格式时采用 Conventional Commits：`<type>(<scope>): <description>`，scope 可省略，描述语言沿用当前沟通语言。选择能解释主要目的的 type，破坏性变更明确说明。
- 不把某一种技术栈的目录结构、文案变更分类、检查命令或 hook 行为套到其他项目。
- 若仓库配置引用了外部规则而无法确认其实际内容，注明未确认项，不编造校验条件或放宽门禁。

## 盘点与分组

分别读取 staged、unstaged 和未跟踪文件，避免用 `git diff HEAD` 漏掉暂存与未暂存相互抵消的变化：

```bash
git status --short
git diff --cached
git diff
git ls-files --others --exclude-standard
```

逐一读取候选新文件，检查是否存在生成物、敏感内容或与本任务无关的改动。只纳入授权范围，保留用户原暂存状态。

按可独立回滚的业务目的分组，生成物与其来源或登记放在同组。测试生命周期遵循目标仓库约定：采用临时验证策略时，可以临时编写并执行测试，验证通过后删除测试及专用夹具，不提交到远程；提交保留必要验证结论。不要机械按文件类型拆分，也不要用“同属本次重构”合并可独立回滚的多个功能。

对每组统计文件数、增删行数、目录和功能范围，执行仓库规定的规模门禁。未设置数值阈值时根据回滚边界与可审查性判断，不人为套用其他项目的限制。大规模变更先按功能域，再按独立变更细分；二进制文件注明数量与用途，不虚构行数。

同一文件属于多个组时优先按 hunk 精确暂存。无法可靠分离时说明依赖和归属，不能据此把整个工作区合为一个提交。

## 可审阅方案

展示每组提交信息、文件数 / 增删行数、明确文件范围、依赖和验证证据；同时说明未纳入文件。方案应覆盖全部获授权文件，不能用宽泛目录掩盖遗漏。

只要方案时到此结束。已有有效提交授权时继续执行，无须再次询问；方案外行为需另有依据。

## 本地提交

1. 核对当前暂存内容；已有无关暂存项不能夹带提交，也不能擅自清空。无法隔离时说明阻塞。
2. 仅暂存该组文件或 hunk，复查实际 staged diff、规模及归属；采用临时测试策略的仓库还须确认测试已在验证通过后清理，暂存区不含测试及专用夹具。
3. 运行目标仓库要求的检查并核对结果；证据仍对应相同代码状态且覆盖充分时复用。实际 hook 行为以配置与输出为准，不因存在 hook 就声称检查已通过。
4. 提交后记录 commit ID，并核对剩余工作区与暂存内容。

范围超出方案时，只撤回本次操作新增的暂存内容并重新分组，保留用户原暂存状态。禁止跳过 hook、使用 `--no-verify` 或通过改代码、改检查规则来凑提交成功。

若 hook 修改了文件，先核对变化、归属和验证，不能自动把所有新增修改暂存。校验失败应说明具体原因；提交消息可按真实规则修正，业务修复需要相应任务授权。

## 远程推送

仅已有推送授权时执行。核对 remote、分支、upstream 和全部待推送提交；推送会带上尚未同步的祖先提交，范围外提交须先说明并补足授权。没有 upstream 时不猜测目标；拒绝或失败时报告原因，不自动改用强推。

## 交付

分别报告方案、本地提交与推送是否执行、提交 ID、实际目标、未纳入文件及未完成原因。本地成功不能描述为远端已更新。
