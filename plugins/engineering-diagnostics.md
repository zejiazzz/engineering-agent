# 工程诊断

根据任务选择对应章节。先确认要回答的问题、涉及仓库与分支、统计对象及可用数据。回溯型任务要说明时间范围、时区和边界。缺省范围且范围会改变结论时先对齐用户，或在可反查的范围内试查并声明覆盖边界。PR、缺陷和事故记录从已授权的数据源读取。证据不足时列出数据缺口及可做的补验。

## 架构演变与历史包袱

1. 从当前入口、边界和主要调用链建立现状。用 Git 历史定位引入、迁移和行为变化，再查对应 PR、决策记录、问题和事故，核对当时约束与取舍。
2. 按证据说明设计动机、目前仍生效的条件，以及曾经依赖它的消费者。缺少 PR、仓库是浅克隆或只能找到代码变化时，标明推断和覆盖范围。
3. 对候选历史包袱验证当前消费者、动态调用、老数据、兼容契约和运行配置，给出能证伪移除判断的反例。安全性取决于验证结果，列出迁移、验收与回退条件。

## 项目交接与认知成本

以刚接手的工程师视角走通三个任务：找到一个正常入口、跟踪一次业务行为、执行相关验证。记录必须阅读的文件、跳转与隐含前提，指出命名冲突、职责交叉、过度抽象或无从发现的依赖。按出现频率、理解成本和简化风险提出改进，优先验证高频入口是否更易定位和维护。

## PR 流转效率

1. 定义统计口径，例如指定窗口内合并的 PR。处理分页，记录覆盖数，将草稿、未完成、跨窗口和数据缺失的记录按实际口径标明。
2. 分别测量可取证的阶段，例如就绪到首次有效审查、审查到更新、CI 等待与执行、批准到合并。说明哪些阶段会重叠。按同口径列出耗时最长的 PR，并提供中位数或分位数等基线供对比。
3. 回看慢例的实际事件，区分交接等待、CI、外部依赖、方案返工和 PR 规模。提出可改变的流程瓶颈和验证指标，个人归因须有具体证据。

## 缺陷、返工和回滚复盘

1. 汇总指定期间的 Bug、返工、回滚和重复修改，关联重复事件与修复提交，避免把同一问题的多次记录当成多起事故。
2. 用时间线、复现和跨事件对照验证共同根因，寻找本应发现或阻止问题的环节。检查反例，避免把共同症状当成共同原因。
3. 按复发频率、影响及执行成本选择措施。明确的约束写入项目规则，可重复判断的条件交给测试、CI 或自动化，需要人工取证和协调的流程沉淀为 Skill。沿用项目实际入口，记录验证方法、误报及维护归属。用户要求落实时，落地并验证对应措施。

交付时给出覆盖范围、关键证据、影响最大的结论和可验证措施。建议涉及多个模块时，核对其后续影响、实施成本与回退路径。
